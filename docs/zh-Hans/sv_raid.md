# 太晶团体战

本地太晶团体战是《朱／紫》在 LDN 场景 7 中建立的会话，最多容纳四个站点。主机运行大厅，再向每个参与者发送一条初始化消息，包含四位玩家的宝可梦、首领及其 RaidPoint；各游戏机独立运行战斗。`bin/sv_host.py --raid-seed` 创建团体战供实机加入，`bin/sv_join.py --raid-pokemon` 加入游戏机主持的团体战。在两种模式中，本程序的玩家都会在对战开始时离开，宝可梦则作为游戏机的 AI 伙伴继续战斗。本文地址为《朱》4.0.0 解压后的 `main` 中的偏移；《紫》4.0.0 的相同代码位于相同偏移（[《朱／紫》](sv.md)）。

## 主持团体战

主机广播场景 7、四名参与者和连接密码 4970。游戏机通过 X → 宝可入口站 → 太晶团体战 → 离线搜索加入。`--raid-seed` 与四个上下文参数共同选择团体战（[种子](#the-seed)）；`--raid-pokemon` 指定我方出战宝可梦的队伍记录，由 PKHeX 检查；重复使用 `--raid-reward ITEM:QUANTITY` 可将种子的默认奖励替换为指定道具和数量。道具必须能放入《朱／紫》背包，即 PKHeX 辅助程序的 `bag` 列表：包括重要物品以外的所有口袋，并排除未发布道具。应用的“太晶团体战（主机）”入口携带以下参数。

    --channel 1 --scene-id 7 --max-participants 4 --code 4970 --scarlet-response --session-flags 0
    --session-packet-id 1 --no-session-ack --join-seq 0 --update-seq 0 --update-delay 0.02
    --rtt-probe --clock --net-stations 4 --record-delay 0.1 --record-spacing 0.003
    --host-player-id 00000000000000010000000000000000

团体战主机与交换主机在消息目标和发送时机上有所不同：

| | 团体战主机 |
|---|---|
| 发往网状网络的消息（RTT、0x80、0x81）、Session 站点列表 | 发往子网广播地址，而非游戏机地址（通过 ldn_mitm 时使用单播，因为它不向对端传递广播） |
| Net 0x11 | 使用同一序列号，重复发送直到收到 0x12 |
| 站点列表中的游戏机条目 | 使用游戏机加入请求中指定的玩家；使用占位玩家会导致游戏机已入座却未出现在大厅 |
| 站点列表 | 每 2 秒重发，直到收到游戏机的类型 6 |
| 开场 | 收到类型 6 后才发送：最先的十一条批量确认、0x81 端口 5 打开消息和 RTT 请求放入一个数据包；随后发送 0x81 端口 1 打开消息、通道表及端口 2 类型 6；20 毫秒后发送身份数据，每条记录间隔 3 毫秒 |
| 端口 2 类型 3 | 回应两条类型 9：主机站点代码为 0，游戏机站点代码为 1 |

开场的 0x7C、0x81 端口 5 和 0x80 端口 2 消息每 0.25 秒重复发送，直到得到确认；主机发出的每条确认都声明该数据流中尚未确认的最低序列号。

形如 `10 00` 后接十四个随机字节的玩家 ID，未能让实机发送类型 6；匿名 ID `00000000000000010000000000000000`（`pia_connect.DEFAULT_PLAYER_ID`）则使其成功入座。

## 大厅

团体战消息是 0x80 端口 0 上的游戏消息：一个 u16 处理程序键、一个种类字节和一个步骤字节（[交换流程](sv.md#the-trade)），后接游戏序列化器的标头与载荷。

| 字节位置 | 字段 |
|---|---|
| 0 | 处理程序键，u16 |
| 2 | 种类、步骤：一个 u16 消息 ID（0x012f 初始化，0x0193 对战开始） |
| 4 | 每个发送方独立的 u16 计数器，由 `0xa583fc` 在每次发送时递增：实机主机大厅从 0x0105 到 0x010e，加入方从 1、2、3……递增 |
| 6 | 压缩方式，u32：0 为无压缩，2 为 LZ4 |
| 10 | 载荷未压缩大小，u32 |
| 14 | 网络对象 ID，u16，发送方 `0x14ede48` 未找到对象时为零 |
| 16 | 构造函数从不写入的两个填充字节（实机消息中的堆残留数据） |
| 18 | 载荷 |

| 键 | 种类 | 内容 |
|---|---|---|
| 0x3380 | 0x2c | 团体战描述：种类（DevID）、形态、星级、太晶属性、性别、遭遇记录编号 |
| 0x3380 | 0x2d | 参与者状态：0x18 空闲、0x01 准备就绪、0x0c 主机开始、0x0d 加入方回应开始 |
| 0x3380 | 0x2e | 参与者的宝可梦，加密后的 344 字节队伍记录 |
| 0x3380 | 0x2f | 战斗初始化数据 |
| 0x3380 | 0x30 | 大厅剩余时间，单位为秒（从 0x91 递减） |
| 0x0132 | 0x6e, 0x73 | 游戏机正在加载战斗，以及加载完成 |
| 0x3480 | 0x93 | 战斗开始 |
| 0x007b | 0x13 | 主机在 0x3480 后发送的战斗开始消息 |

标头对应消息对象的 `+0x40..+0x4f`。接收路径 `0x18bec54` 将 ID、计数器和对象 ID 复制回对象，不比较这些字段；不检查 LZ4 返回值，未压缩大小仅用作输出容量。

键 0x007b 的战斗开始帧包含 12 字节端口地址（三个 u32）、一个 u32 长度和载荷；载荷前 32 字节为 `0x1227714` 原样复制的标头结构：0x00 的 u32 类型、0x08 和 0x10 的 u64、0x18 和 0x19 的 u8，以及 0x04 和 0x1a..0x1f 的填充。消息 15 在 0x18 保存 `05 05`，随后为填充 `07 26 5a 00 00 00`；消息 16（类型 0x46，构建器 `0x2898350`）的构建器从未写入的填充中保存 `ceaf29`。读取方 `0xf5a2fc`（+0、+8、+0x10、+0x18，最后一项接受 5 或接收者自身索引）和类型分派 `0xe10088`（0x46 处理程序 `0x2897afc`）不读取填充。`0x14ab234` 在接收者没有端口注册该地址时丢弃帧：消息 15 发往 (0x2713, 1, 2)，消息 16 至 20 发往 (0x2713, 3, 5)，0x2713 是对象 `+0x40` 的运行时 u32，写入方未追踪。
模拟《朱》4.0.0 接收填充清零的消息 13、15、16 后，首次发送就确认所有战斗开始消息，并以主机宝可梦开始对战，与使用实机字节时相同。
模拟《朱》4.0.0 在主机发送消息 15、16 后 13 毫秒进入保留分支 `0x14ab210`：`0x14ab234` 匹配战斗开始帧地址，`0x14ab298` 保存它。

对战按类型读取消息 16。读取方 `0xe0fd68` 弹出帧，在标头 +0x08 的 u64 为 0 时按 +0x00 类型分派（`0xe10088`）：类型 0x46 以 `[reader+0x48]` 为唯一参数调用 `0x2897afc`，`0x2897afc` 在对象 `+0x71` 写入 1。该参数是逐帧更新 `0x289358c` 自身的对象：`0xfa4bb4` 通过初始化程序 `0x28950c8` 创建（`+0x40` 为战斗状态机，此处称 `sm`；`+0x48` 为推进对象 `[sm+0xa8]`，`+0x50` 为读取方 `[sm+0xb0]`），保存到 `[sm+0x148]`（`0xfa4c18`），并赋给 `reader+0x48`（`0xfa4c68` 处的 `0x2892ab4`）。状态 `0x28932a4` 以 `[sm+0x148]` 调用更新（`0x28932d0`）。更新读取 `+0x71`：为 0 时驱动读取方（`0xe0f014`），调用 `0xfc363c([+0x48], 0)`；为 1 时停止驱动，每帧调用 `0xfc363c([+0x48], 1)`，返回 true 时由 `0x28935b8` 清零。参数为 1 时，`0xfc363c` 从 `+0xa8` 的来源取出项目，在 `[+0xb8]+0xa0` 目标为空时交给 `+0xa0` 和 `+0xb8` 的目标。目标包含双端队列（map `+0x60`、起点 `+0x98`、大小 `+0xa0`），每帧推进各元素的 vf `+0x68`（`0xfc38dc`）。更新结果未使用（`0x28932d4`），该路径不会写状态机 `+0x68` 的状态。
模拟《朱》4.0.0 在类型 0x46 分支弹出的帧携带主机写入消息 16 填充的标记（`46000000 d16a1616`、`0500 161616161616`），因此该帧就是消息 16。弹出发生于网络断开、Error 7 提示之后，首次指令菜单之前，来自更新自身的驱动调用（返回地址 `0x28935d0`，随后 `0x28932d4`）。

4.0.0 的判断逻辑不读取填充。接收路径载入序列化器标头末两字节（`0x18bec98`），不比较就存入 `+0x4e`（`0x18bece4`）；49 个消息类中，只有序列化器 `0x290b150` 和 `0x14c7904` 读取 `+0x4e`，用途是写出标头。战斗开始读取方 `0xe0fd68`、`0xe106a4`、`0xf5a2fc`、`0xf5a810`、`0xf5bc10` 读取 32 字节标头的 +0x00、+0x08、+0x10、+0x18、+0x19；`0xf5a454` 和 `0xf5ae40` 将全部 32 字节复制到 `0xf5bb4c` 重发的帧，不比较它们。传输复制（`0x14ab150`、`0x14ab234`、`0x16a319c`）只比较 12 字节地址。

团体战主机在 0x7C 端口 1 公布的通道表包含六个键，使用 zlib 压缩：连接交换的四个键（`0x007b`、`0x0132`、`0x0232`、`0x0332`），以及 `0x3380`、`0x3480`。实机加入方分两条消息公布它们：先发送四个键，0.79 秒后发送团体战的两个键。端口 2 携带主机的类型 6：种类 5、容量 4 下的类型 7 会话块，后接四个槽位的列表，首个槽位为主机站点 ID（`port2.build_session`）。

`pokeldn.sv.raid.RaidHost` 按顺序释放主机的二十条消息，每条消息均依据端口 2 回应后的时刻，并等待游戏机完成上一阶段：

| 序列号 | 消息 | 释放条件 |
|---|---|---|
| 1 | 描述信息（zlib，INITIALIZED） | 游戏机自己的大厅宝可梦（0x2e） |
| 2, 3 | 状态 0x18、我方宝可梦 | |
| 4, 5, 6 | 计时器 0x91、0x90、0x8f | 0.73、1.76、2.75 秒 |
| 7 | 状态 0x01 | 3.19 秒 |
| 8, 9 | 计时器 0x8e、0x8d | 3.76、4.79 秒 |
| 10 | 状态 0x0c，开始 | 5.39 秒 |
| | Net 0x50，属性状态 7 | 游戏机的状态 0x0d |
| | Session 站点列表，序列号 1 | 游戏机的 Net 0x51 |
| 11, 12 | 初始化数据，两个分片 | 游戏机针对它发送的类型 6 |
| 13 | 加载完成，`0x320173` | 游戏机的 0x6e 或 0x73 |
| 14 | 战斗开始，`0x803493` | 游戏机的 0x73 |
| 15 到 20 | 战斗开始消息 | 游戏机的 0x93；随后间隔 0、0.10、0.12、0.16、0.18 秒 |

受阶段条件控制的消息在对应里程碑后 50 毫秒发送；Net 0x50 和站点列表每 0.5 秒重发，直到得到回应，团体战消息也每 0.5 秒重发，直到得到确认。实机曾对初始化消息回应 0x73 而不发送 0x6e，因此消息 13 等待两者中的任一种。

消息 20 发送五秒后，主机像离开的实机主机一样将网络移交给游戏机（[离开](sv.md#leaving)）：每秒发送指定游戏机的 Session 类型 7，直到收到其类型 8；每 0.5 秒发送处于迁移形式的 Net 0x11，直到收到其 0x12；每 0.3 秒发送 NetStartHostMigration `01400000`，直到游戏机离开网络或经过 4 秒。如果改为在消息 20 后 5 秒销毁网络，四次实机团体战中有一次在战斗开始时显示 2318-0006，之后战斗继续以离线方式运行。

Net 0x50 使用交换主机的属性主体（`NET_PROPERTY_BODY`），其中序列号为 1，包含网络 ID，第 27 字节为 7，并在 +38 处携带主机的 132 字节应用数据；整体以 zlib 压缩，消息标志为 0x31。在 0x31 下不压缩发送时，未得到 0x51。

## 战斗初始化数据

消息 0x2f 携带一条 0xaa0 字节记录，以 LZ4 压缩（仅使用块格式，`pokeldn.sv.lz4`）：

| 偏移 | 大小 | 内容 |
|---|---|---|
| 0x000 | 4 x 0x158 | 四名参与者的加密队伍记录，主机位于槽位 0 |
| 0x560 | 0x158 | 首领的队伍记录 |
| 0x6b8 | 0x3e8 | RaidPoint |

序列化器 `0xe327fc` 通过 `0xe329b4` 从消息对象的 `+0x440`、`+0x448`、`+0x450`、`+0x458` 和 `+0x50` 写入五条记录（每条 0x158 字节），再写入 `+0x58` 的四个四字和 `+0x78` 的 0x3c8 字节。对象大小为 0x460 字节，由 `0x18bb4fc` 创建，`0x18bb5f8` 设置类型；`0x1592b7c` 写入序列化器标头并选择压缩方式，`0x1592dac` 和 `0x1592e80` 执行 LZ4（`0x71d940`）。RaidPoint 整体复制：`0x1bae670` 调用 `0x1bae760`，通过反射字段读取器 `0x1baff98`（取 `+8` 处指针，或取清零的 0x3c8 字节单例）取得数据，再由 `0x1bb0018` 写入 `+0x78`。

空参与者槽保存种类 0、等级 1、昵称为 `Egg`、太晶属性 19、语言 2、当前 HP 11，以及能力值 11/5/5/5/5/5；每次实机初始化都使用相同记录。将空槽全部清零会使实机在战斗开始时崩溃。加入方槽位 1 的记录来自其大厅消息 0x2e。实机主机在 1395 字节处分割消息，第二个分片使用 zlib 压缩。

RaidPoint 中相对其起点的偏移如下：

| 偏移 | 大小 | 内容 |
|---|---|---|
| 0x000 | 24 | 地点名称，ASCII，`RaidPoint_` 加后缀（接受 `RaidPoint_POKELDN_0`） |
| 0x018 | u32 | 0x40（某个实机黑色结晶地点保存 `0x458F9952`；接受 0x40） |
| 0x020 | 4 x u32 | 星级、结晶（0 普通、1 黑色）、记录的 `captureRate`（1）和 `captureLv` |
| 0x030 | 7 x u32 | 记录的 `raidTimeData`：active（布尔值）、`gameLimit`、`clientLimit`、`commandLimit`、`pokeReviveTime`、`aiIntervalTime`、`aiIntervalRand`；`raid_point` 写入零 |
| 0x04c | 37 x u32 | 首领行动配置：HP 系数、屏障的九个值、六项额外行动（行动、时机、值、招式），以及双重行动的三个值 |
| 0x0e4 | 45 x 16 | 奖励行：道具、数量、稀有道具标志、适用对象 |
| 0x3b4 | u8 | 实机普通结晶为 0，黑色结晶为 1 |
| 0x3b8 | 7 x u32 | 星级、种类（DevID）、形态、性别、等级、0、太晶属性 |
| 0x3d8 | u64 | 实机地点中非零，`raid_point` 写入零 |
| 0x3e0 | u32 | 所有已见实机地点均为 4；`raid_point` 写入 2，实机《朱》可接受 |

团体战表中，全部六星记录的 `raidTimeData` 均启用，`gameLimit` 为 450、`commandLimit` 为 60；全部一星记录未启用，`gameLimit` 为 300，其余为零。一个实机黑色结晶（记录 6045）保存 1、450、0、60；一个实机三星结晶（记录 3019）保存未启用布尔字节、三个残留字节，再后为零。
两个实机结晶的 0x3b5..0x3b7、0x3d4..0x3d7 和 0x3e4..0x3e7 均保存残留字节。

行动配置来自游戏团体战表中该记录的 `bossDesc`，顺序如上。行动值为：0 无、1 重置首领能力变化、2 重置玩家能力变化、3 使用招式、4 吸取太晶珠能量；时机值为：0 无、1 时间、2 HP。一到六星的 HP 系数分别为 500、500、800、1200、2000 和 2500。

实机地点的奖励行依次为种子的固定奖励、随机抽取奖励、主机加成奖励：三行适用对象 4、一行适用对象 5。固定行的对象来自奖励表 `SubjectType`（0 所有玩家、1 主机、2 加入方、3 一次）；游戏枚举 `RaidRewardItemSubjectType` 没有 4 或 5。两个实机地点的对象 4 行均为同一生成器额外抽取三次，对象 5 行则为首领太晶碎片，数量由 `RaidGemItemRewardBoost` 按难度给出（一至七星分别为 0、0、2、5、10、12、0；三星 2，六星 12）。餐力表读取方 `0xef885c` 读取一个团体战字段 `AddRewardSlots`。奖励行第三个字在银色王冠随机行中为 1，其他为 0。

模拟《朱》4.0.0 加入方接收适用对象 0 至 5 各一行时，奖励画面列出 0、2、3、5，不列 1、4。餐力“团战力：幽灵 Lv. 1”生效时，面对钢太晶首领不列对象 4，面对幽灵太晶首领则列出；发送三行对象 4 时仅列第一行。

《朱》4.0.0 的 Lua 奖励过滤函数 `C07C34FC3B976E5A7.F316609DEA110601D`（源代码第 78707 至 78765 行）为所有玩家保留适用对象 0，为主机保留对象 1，为加入方保留对象 2；一次性奖励的资格参数为真时保留对象 3。它保留前 N 行对象 4 的奖励，其中 N 是当前生效且与首领太晶属性匹配的团战力最高等级。餐力种类 5 为团战力，属性 18 匹配所有太晶属性。对象 5 要求接收方背包中持有道具 2481，即晶耀护符。每遇到一行对象 4，行计数器都会递增。测试框架提供原生环境查询函数后，执行未经修改的 Lua 函数：团战力等级 0 至 3 分别保留零、一、二、三行对象 4，对主机和加入方均如此，与是否持有护符无关。属性不匹配时不保留任何行；多个匹配的餐力同时生效时采用最高等级。

若主机要复现零售版游戏的奖励构建方式，应保留每行固定奖励的适用对象，以及每行奖励的稀有道具标志；普通随机抽取奖励使用对象 0，随后继续同一抽取序列，追加三行对象 4 的随机奖励。对应难度的太晶碎片加成数量大于零时，再追加对象 5 的奖励。每位接收方分别按自身餐力和护符判断领取资格。

计时器初始化函数 `C2D7F486425487755.F0C64BA9B6853E61A`（源代码第 79486 至 79513 行）在 `raidTimeData.active` 为真时使用传入的时间字段；为假时，团体战默认使用游戏时限 300、指令时限 60、客户端时限 0、复活时间 30、AI 间隔 17 和 AI 间隔随机幅度 6。将六星表的数据传入未经修改的 Lua 函数执行，上述值依次为 450、60、0、0、0、0；RaidPoint 全部为零时采用默认值。两个函数均位于 Lua 代码块 `be21e65463b9a98f`，SHA-256 为 `c1a4f4e2625912cf0b739a642a79ba3357df0557a544b92da22a6cb139de2815`。

`raid_point` 将种子奖励（或指定奖励）的对象全部写为 0，不添加加成行，因此加入方获得每一行，包括原本主机独享的奖励。实测将某行改为先机球 ×500，清空其他行并保留一行加成奖励后，游戏机按写入内容发放奖励。

## 种子

团体战由 32 位种子和游戏机状态决定：版本、地区（帕底亚、北上乡、蓝莓学园，表前缀分别为 `""`、`su1_`、`su2_`）、剧情进度及结晶。xoroshiro128+ 从种子和常量 `0x82A2B175229D6A5B`（`0xe29340`）开始；第一次抽取范围为一百个值，按剧情阶段的边界决定普通结晶的星级（黑色结晶固定为六星）；第二次依据该星级和版本中的出现概率选择遭遇。`0xe29404` 以 `%sdifficulty_%02d` 构建表名，并将记录传给读取 `raidEnemyInfo` 的 `0x1eab5e4`；`0x2935b68` 遍历全部三个前缀和六个等级。随后，相同种子重新初始化 xoroshiro，依次生成首领的 EC（种子低半部分加 `0x229D6A5B`，因此可从首领记录反推出种子）、模拟训练家 ID、PID、满个体值项、其他个体值、特性、性别、性格（颤弦蝾螈从对应形态的列表中选择）、身高、体重及体型大小，与 PKHeX 的 `Encounter9RNG.GenerateData` 相同；太晶属性和奖励抽取各自再使用一个重新初始化的生成器。

`pokeldn.sv.raid_encounter` 基于 `pokeldn/sv/data/raid_base.json` 实现上述流程；数据由 `scripts/gen_sv_raid_data.py` 根据 Tera-Finder 的遭遇列表和奖励表、PKHeX 种族数据，以及游戏 RomFS 中十八张 `raid_enemy_XX_array` 表生成（`arc/worlddataraidraid_gem_item_reward_boostdata.bin.trpak`，带自身 `.bfbs` 架构的 FlatBuffers）。全部上下文的 12600 多个种子，首领均与 PKHeX.Core 26.8.26 逐字段相同，包括帕底亚六种遭遇（记录 5094 到 5099）：实机表的太晶规则为 0（种类自身属性），PKHeX 保存为 1（任意属性）。结晶构建器 `0xe26ff0` 读取 `gemType`，规则 0 和 1 都从 18 种属性随机选择（`0xe27414` 的 `cmp w9, #2`，重复抽取直至小于 18），与 PKHeX 相同；通用转换器 `0x160e108` 将 0 视为种类属性，但不在团体战路径上。种子 `BD13FB43`（紫、帕底亚、四星）生成的首领记录与实机初始化数据逐字节相同；`7B741233`（朱、帕底亚、五星）与法语实机《朱》相同，只有昵称与语言不同：实机写入自身语言和对应的种类名称（`Embrylex`、3），生成器使用英语（2）。游戏机始终以自身语言显示首领名称。

团体战表中的种类使用游戏的 DevID：到 916 为止与全国图鉴编号相同，从 917 起使用游戏自己的顺序（小锻匠 957 对应 1000），转换由 `gen9.internal_index` 完成。描述信息和 RaidPoint 同样携带 DevID：向实机《朱》发送种类 1000 的描述和 RaidPoint 后，大厅显示并在战斗中出现小锻匠。

黑色结晶记录的战斗等级为 90，携带努力值（例如防御 128、特防 128），捕获等级为 75；普通结晶记录的两个等级相同，努力值为零。初始化数据中的首领记录和 RaidPoint 概要携带战斗等级和努力值，RaidPoint 的 `+0x2c` 携带捕获等级。种子 `09F3E337`（朱、帕底亚）生成的黑色结晶首领与法语实机《朱》一致，只有昵称和语言不同。

## 查找种子

应用的团体战种子字段会显示当前上下文下生成的首领和奖励。“查找团体战”最多搜索一百万组种子与上下文组合（`pokeldn.sv.raid_search`），可筛选种类、星级、太晶属性、性格、性别、异色和个体值范围，并按首领能力值评分排序：HP 乘双防之和、HP 乘任一防御、较高的攻击能力值，或能力值总和。不指定种类时，每种宝可梦只保留一个结果。搜索速度约为每秒 40 000 个种子。

## 加入团体战

`bin/sv_join.py --raid-pokemon FILE` 加入场景 7 的网络，并作为加入方参与。游戏机玩家调查结晶，选择“大家一起挑战”后等待；应用的“太晶团体战（加入）”入口负责运行加入端。`pokeldn.sv.raid.RaidGuest` 和加入端按以下顺序执行：

| 步骤 | 加入方行为 |
|---|---|
| Net | 在消息标志 0x11 下回应 0x11 和 0x50 |
| Session | 不回应加入响应附带的站点列表，至少 1 秒后确认其重发，之后确认每个列表，并发送第 9 字节已设置的时钟请求 |
| 通道 | 将主机的六键表拆为四个键和团体战的两个键，公布四个键；0.24 秒后加入端口 2，表公布后 0.79 秒公布团体战键；将 0x7C 确认延迟 0.25 秒 |
| 身份 | 入座后 0.44 秒发送标准记录集（`pokeldn.sv.reference`），记录 1 使用训练家名称 |
| 大厅 | 再过 0.27 秒发送状态 0x18 和自身宝可梦；2 秒后发送状态 0x01 |
| 开始 | 收到主机的状态 0x0c 后发送状态 0x0d；准备就绪时就发送 0x0d 的加入方得到确认，但始终未显示为准备就绪 |
| 战斗 | 确认主机的 0x3480 0x93，每 0.5 秒发送 Session 类型 3 离开请求，直到收到类型 4（最多四次），然后离开网络；战斗中的实机《朱》未回应其中任何一次 |

在实机主机上，加入方以训练家名称出现在大厅，变为准备就绪，主机随后可以开始战斗；其宝可梦留在战斗中。
